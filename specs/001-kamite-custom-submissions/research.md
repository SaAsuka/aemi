# Research: 案件ごとの提出項目を応募フォームで受け取る

調査日: 2026-10-10　対象: `vozel-test`（origin/main との内容差は9ファイル・本機能に関係なし）

## 調査で分かった既存の問題（本機能の前提に影響するもの）

| # | 問題 | 場所 | 本機能への影響 |
|---|---|---|---|
| P1 | 応募処理がログイン中の本人を確かめず、フォームの `talentId` をそのまま使う。`status` もフォームから受け取るため、タレントが自分で「合格」の状態で応募を作れる | `src/lib/actions/application.ts:114`、`src/lib/validations/application.ts` | 他人になりすまして応募できる・自分で「合格」を作れる。自由項目の回答も他人名義で作れてしまう。FR-018 で必ず塞ぐ |
| P2 | ファイル配信 `/api/blob` に権限確認がない。保存先URLが分かれば誰でも中身・7日有効の署名付きURLを取れる | `src/app/api/blob/route.ts` | 「提出物は管理者と本人だけ」（FR-019）が今は成り立っていない。提出物（`applications/`）だけ絞る |
| P3 | アップロード `/api/upload` に権限確認がない | `src/app/api/upload/route.ts` | 新しいアップロード経路では権限確認を入れる。既存経路は今回触らない |

## R1. 自由項目・回答の保存方法

- **Decision**: `jobs.submissionFields`（Json?）と `applications.submissionAnswers`（Json?）の2カラムを追加する。中身の形は zod で定義し、読み書きのたびに必ず通す（`src/lib/submission-fields.ts`）
- **Rationale**: 追加は空を許すカラムだけで、既存のデータ・クエリに影響しない（最優先の前提）。KAMITE再送時は配列ごと置き換えるだけで済む。回答に「回答時点の項目名」を持たせやすい
- **Alternatives considered**: 項目テーブル＋回答テーブルを新設 → DBが形を守れる利点はあるが、テーブル2つ・並べ替え・再送時の突き合わせが重く、件数（1案件最大50項目）に対して過剰。既存の `JobRequirement` を拡張 → `@@unique([jobId, category])` と enum が固定4種類前提で、既存の動きを壊す危険が大きい

## R2. 項目の判別（名前・年齢・身長・コンポジ）

- **Decision**: 判別は純粋関数 `detectAutofill(label, kind)` で行い、**保存時に結果を `autofill` に書き込む**（表示のたびには判定しない）。管理画面の案件編集で `autofill` を手で直せる
- 判定語（初期値。テスト環境で山中さんの実データを見て調整）:
  - `COMPOSITE`: 「プロフィール」または「コンポジ」を含む（種類は問わない。「プロフィール写真」も含む。最初の依頼どおり・2026-10-10 決定。普通の写真にしたい案件は管理者が案件編集で直す）
  - `NAME`: 空白・記号・「お」「ご」を除いた項目名が「名前」「氏名」に一致し、種類が TEXT。「保護者」「緊急」「連絡先」「事務所」「担当」「ふりがな」「フリガナ」「カナ」「ローマ字」を含むものは除外（本人以外の名前・読み仮名を本人の名前で埋めないため）
  - `AGE`: 「年齢」を含み、種類が TEXT
  - `HEIGHT`: 「身長」を含み、種類が TEXT
  - 上記以外・種類が合わないもの: `null`
- KAMITEから同じ案件が再送されたとき、同じ `key` の項目は**管理者が直した `autofill` を引き継ぐ**（`autofillOverridden: true` の項目だけ。自動判定のままの項目は再判定）
- **Rationale**: KAMITEは種類しか送らないため名前で判断するしかないが、誤判定を管理者が直せるようにして弱さを補う。純粋関数なのでテストで固められる（開発原則 第5条）
- **Alternatives considered**: KAMITE側に「何の情報か」を送ってもらう → KAMITE側は変えない前提（FR-030）

## R3. 項目のキー

- **Decision**: KAMITE由来は `k_` + 項目名の短いハッシュ（同じ項目名が複数あれば出現順の番号を足す）。管理画面で作った項目は `v_` + ランダム8文字
- **Rationale**: KAMITE は項目IDを送らない。項目名からキーを作れば、再送で同じ項目名ならキーが変わらず、既存の回答と結び付いたままになる
- **Alternatives considered**: 毎回ランダム → 再送のたびに既存回答が「現在の案件にない項目」扱いになる

## R4. 本人確認（FR-018）

- **Decision**: 応募処理の先頭で「誰として応募するか」を受け付け側で決める関数 `resolveApplicant()` を通す
  - 管理者セッション → フォームの `talentId` を採用（代理応募。`status` も採用。コンポジットの有無は問わない＝今の代理応募画面と同じ）。**自由項目の必須チェックと「入力中に項目が変わったか」の確認もしない**（代理応募の画面に自由項目の入力欄が無いため。回答なしで応募を作り `hasMissingAnswers` を立て、管理者が応募詳細で後から入れる。analyze A1）
  - どの経路でも、本人確認ができずに拒否した呼び出しは `form_error_logs` に記録せず `logger.warn` にだけ出す（回数制限のない記録で外からテーブルを埋められないようにするため。analyze A3）
  - タレントセッション → セッションの `talentId`。フォームの `talentId` は無視。`status` は `APPLIED` 固定。コンポジット必須
  - 専用リンク（`t`）→ `getTalentByToken(t)` の本人（ACTIVEのみ）。`status` は `APPLIED` 固定。コンポジット必須。フォームに `t` を hidden で持たせる
  - どれでもない → 拒否
- **Rationale**: P1 の穴をこの機能で塞ぐ。管理画面の代理応募（`new-application-dialog.tsx`）は同じ関数を使っており、壊さない必要がある。代理応募画面には今コンポジットの確認が無いため、代理応募にコンポジット必須を課すと既存の動きが変わる（analyze I1）
- **Alternatives considered**: タレント用と管理者用で関数を分ける → 修正範囲が増え、既存の管理画面の呼び出しを変える必要がある

## R5. アップロード方式（4.5MB問題）

- **Decision**: 自由項目のファイルは**ブラウザからストレージ（Supabase Storage）へ直接アップロード**する。サーバーは「この人がこの場所に上げてよい」を確認して、1回限りの署名付きアップロードURLを発行するだけ（新設 `POST /api/submissions/upload-url`）。保存先は `applications/{talentId}/{jobId}/{key}-{時刻}.{拡張子}`
- 写真の項目は、アップロード前にブラウザで長辺2400px・JPEGに縮小する（HEICをブラウザが読めない場合は縮小せずそのまま上げる）。容量・枚数のための縮小で、4.5MB対策は直接アップロードで解決する
- **止まったとき（無限ロード）**: ストレージへの送信は `XMLHttpRequest` で行い（`fetch` は送信の進み具合が取れないため）、進み具合（％）を表示する。**30秒間まったく進まなければ中止**して `STALLED`（止まった。タレントには「通信の問題」と表示）として扱う。アップロード中は「中止」ボタンを出す。upload-url の発行は15秒で打ち切る
- **Rationale**: 4.5MBの壁をサーバーを通さずに回避できる。権限確認（P3）も新経路で入れられる。既存の `/api/upload` を触らないので既存画面に影響しない。iPhone・LINE内蔵ブラウザはアプリ切り替えで通信が止まりやすく、時間で区切らないと「くるくるが終わらない」状態になる
- **要検証（実装の最初に行う）**: 署名付きアップロードURLへ、公開鍵（anon key）なしで PUT できるか。できない場合は `NEXT_PUBLIC_SUPABASE_ANON_KEY` を追加する（公開して問題ない鍵。テスト・本番それぞれに設定）
- **Alternatives considered**: ブラウザで縮小して4.5MB未満にしてから既存経路 → 動画・PDF・HEICで破綻する。Vercel Blob のクライアントアップロード → 新規分はSupabaseに寄せている現方針と逆行

## R6. 提出物ファイルの閲覧制限（FR-019）

- **Decision**: `/api/blob` で、パスが `applications/` で始まるものだけ権限確認する — 管理者セッション、またはパスの2段目が自分の `talentId` であるタレントセッションのみ許可。それ以外の `applications/` は管理者のみ
- **Rationale**: `applications/` を使っているのは応募の提出物だけ（案件の参考ファイルは `photos/`）。タレントが応募後に提出物を見る画面は無いので、既存の動きを壊さない
- **Alternatives considered**: `/api/blob` 全体に権限確認 → 専用リンク・宣材写真の表示など影響範囲が広く、本機能の範囲外

## R7. プロフィールからの初期値（FR-010〜FR-013）

- **Decision**: 名前・年齢・身長はプロフィールの値を初期値として表示するだけ。**応募フォームからプロフィールは書き換えない**（2026-10-10 決定。名前はフリガナ・請求書〈freee〉に、身長はコンポジットに使われており、応募のついでに変わると影響が大きいため）
- 回答の `origin` は、初期値のまま送られたら `PROFILE`、書き換えられたら `INPUT`。年齢は書き換え不可
- 書き戻しが無いので、トランザクション・値の範囲チェック・「コンポジットが古い可能性」の表示は不要
- **Alternatives considered**: 名前・身長を書き戻す → 上記の影響のため見送り

## R7b. コンポジ項目（FR-015）

- **Decision**: `autofill: COMPOSITE` の項目はフォームに出さず、**回答も作らない**。応募詳細では表示時にタレントの今の `talents.resume` を「コンポジット（登録済みのもの）」として出す（2026-10-10 決定：コンポジットは既存の仕組みなので動きを変えない）
- **Rationale**: 回答に保存しないので、コンポジットの仕組み（登録・作り直し・手動アップロード・応募に必須）に一切触れない。文字・リンクの項目にPDFが入って回答の形が崩れる問題（analyze 最終 H1）も起きない
- **Trade-off**: 応募の後でコンポジットを作り直すと、応募詳細には新しいものが出る（応募時点のものは残らない）

## R7c. 削除時のファイル（FR-031）

- **Decision**: タレント・応募の削除処理には手を入れない。自由項目でアップロードされたファイルは削除時も消さず、ストレージに残る（2026-10-10 決定）。管理者が回答のファイルを差し替えたときも、古いファイルは消さない

## R8. 管理画面の応募詳細と写真の一括ダウンロード

- **Decision**: 新しい画面 `/admin/applications/[id]` を作る。自由項目の回答・既存の4種類の提出物・応募の基本情報を表示。応募管理一覧と案件詳細の応募者欄から「内容を見る」で開く
- **一括ダウンロード**: 管理者のブラウザで写真を集めてZIPにする（`fflate` を追加）。各写真の署名付きURLは既存の `/api/blob?sign=true` で取得し、ストレージから直接取る。ファイル名は `{タレント名}_{項目名}.{拡張子}`（同名は連番）
- **Rationale**: サーバーでZIPを作ると応答本文の4.5MB制限に当たる。ブラウザで作れば大きさの制限がない
- **要検証**: Supabase の署名付きURLをブラウザから fetch できるか（CORS）。できない場合は `/api/blob` 経由で1枚ずつ取得する（1枚が4.5MBを超えると失敗するので、その写真だけ個別ダウンロードに切り替える）
- **Alternatives considered**: 一覧にアコーディオンを足す → 一覧が重くなり、写真のサムネイル・ZIPボタンの置き場がない

## R9. エラー時のふるまいと記録（US6）

- **Decision**:
  - 応募処理のエラーを項目ごとに返す（`{ error: { [fieldKey]: string[] }, message, action }`）。既存の `error` の形（値が文字列配列のオブジェクト）は維持し、管理画面の代理応募ダイアログが今のまま動くようにする
  - 画面は該当項目の下に理由を出し、最初のエラー項目へスクロール
  - アップロードの失敗理由を「大きすぎる」「形式が違う」「通信の問題」「その他」に分類する純粋関数 `classifyUploadError()`
  - 文字の入力・アップロード済みファイルの参照をブラウザの localStorage に途中保存（`apply-draft:{talentId}:{jobId}`）。読み書きは try/catch で囲み、使えなくても動く。応募完了で消す
  - 失敗の記録は新テーブル `form_error_logs`（フォーム名・日時・タレント・案件・項目・理由・端末情報）に保存し、あわせて既存の `logger` にも送る。管理画面 `/admin/error-logs` で直近の記録を一覧できる。秘密情報・提出物の中身・入力値は保存しない
  - **端末側で起きた失敗の報告（analyze C1）**: ストレージへの直接アップロードの失敗・止まった・通信切れはサーバーに届かないので、報告の窓口 `POST /api/form-errors` を新設する。本人確認（タレントセッション・専用リンク・管理者）をし、同じタレントから10分に30件までに制限（`form_error_logs` の件数で判定。サーバーレスでメモリに頼れないため）
  - **受付番号は端末で作る**（`E-` + 英数6文字）。報告が届かなくてもタレントには番号が出る。届かなかった報告は localStorage（`form-error-queue`）にためて、次の操作のとき・応募の送信前に送り直す。サーバーは番号が重複したら作り直して返す
  - **応募の送信が止まったとき（無限ロード）**: 送信は30秒で画面の操作をタレントに戻す（Server Action は止められないので、画面側で待つのをやめる）。そのあと `getMyApplicationStatus(jobId)`（本人確認つき）で応募が完了しているかを確かめ、完了なら完了画面、未完了なら入力を残して「もう一度送信」。再送で二重応募にはならない（`@@unique([talentId, jobId])` と既存の「応募済み」チェック）。タレント本人の再送で「応募済み」になった場合は失敗ではなく完了として扱う
- **Rationale**: 管理者（山中さん）が見られる場所が要る（SC-006）。Axiom は開発者向けで、環境変数が本番に入っているかも未確認。`form` の列を持たせて登録フォームでも同じ記録を使えるようにする
- **Alternatives considered**: Axiom のみ → 管理者が見られない

## R9b. 「未提出あり」の絞り込み（analyze U1）

- **Decision**: `applications.hasMissingAnswers Boolean @default(false)` を追加し、応募の作成・管理者による回答の登録/修正のたびに `hasMissingRequired()` の結果で更新する。一覧の印・絞り込みはこのカラムで行う
- **Rationale**: 応募管理一覧はDBで1ページずつ読んでいるため、読んだ後で絞り込むとページ送り・件数が合わない。JSONの中を検索するクエリは複雑になる。既定 false のカラム追加なので既存には影響しない
- 案件側の項目が後から変わった場合（KAMITE再送・管理者の編集）は再計算しない（応募時点の必須で判断）。管理者が回答を登録したときに再計算する

## R10. KAMITE受け口の変更

- **Decision**: `requirements` を `submissionFields` に変換して保存（R2・R3）。`buildNote` から提出物の文章を外す（FR-004）。受け付ける形式は変えない（FR-030）。再送時は `submissionFields` を丸ごと置き換え、既存の応募の回答は触らない
- 既に note に提出物の文章が入っている過去のKAMITE案件は、次の再送で自然に置き換わる。手で直さない

## R11. マイグレーション

- **Decision**: 開発原則 第3条どおり、`./node_modules/.bin/prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script` で差分を出し、`jobs.submissionFields`・`applications.submissionAnswers`・`applications.hasMissingAnswers`・`form_error_logs` の作成だけが含まれていることを目視確認する。**SQLをユーザーに見せて承認を得てから**テスト環境DBに適用する（自動では書き込まない。analyze C2）。本番は Supabase SQL Editor でユーザーに実行してもらい、`_prisma_migrations` にも記録する
