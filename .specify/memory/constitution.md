# VOZEL (aemi) 開発原則

バージョン: 1.0.0　制定日: 2026-10-03

これは「何を作るか」ではなく「どう作るか」を定めるドキュメントです。
技術的な決まりごと（認証パターン・DBクエリの使い分け等）は `CLAUDE.md` を参照してください。
ここにあるのは、開発の進め方そのものに関する原則です。

---

## 第1条：本番環境は明示的な許可なしに触らない

- `main`（本番）へのマージは、ユーザーの明示的な許可を得てから行う
- 許可を得た場合も、**`vozel-test`を直接`main`にマージしない**。`origin/main`から新しいブランチを切り、
  承認された変更に関係するファイルだけを移植する
- マージ前に必ず `git diff origin/main..HEAD --stat` を見て、触っていないファイルが混ざっていないか、
  削除行が追加行より多くなっていないかを確認する

**なぜ：** `vozel-test`には本番未承認の変更（実験的機能・別タスクの作業途中のもの）が混在しがちで、
ブランチ全体をマージすると意図しない変更まで本番に反映されてしまう。過去に実際、関係ない機能の
テーブルごと削除されかけたことがある。

## 第2条：テスト環境で確認してから本番に出す

- コードの変更は、先に`vozel-test`で動作確認する
- DBスキーマを変更する場合も、先にテスト環境のDBで試す
- 本番への反映は、テストが通り・型チェックが通り・実際に動作確認できてから

## 第3条：データベースのマイグレーションは安全第一

- `prisma migrate dev` はシャドウDBでの履歴再生に失敗することがあるため、まず
  `prisma migrate diff --from-config-datasource --to-schema <schema>` で**差分だけを確認**する
- 差分に無関係な変更（他機能の残骸テーブルの削除等）が混ざっていないか必ず目視確認し、
  意図した1行だけを切り出して適用する
- 手動でSQLを適用したら、`_prisma_migrations`にも適用済みとして記録し、次回の
  `migrate deploy`が重複エラーを起こさないようにする
- 本番DBへの直接アクセスができない場合は、Supabase SQL Editorで管理者に実行してもらう。
  DB書き込みは自動実行せず、必ず内容を提示して確認を取ってから進める

## 第4条：重要な情報はセッションではなくDBに保存する

- ブラウザのセッション（Cookie）は消える前提で設計する。ログイン状態の確認程度の
  軽い情報（`talentId`・`role`等）以外は、セッションに頼らずDBに永続化する
- 「後で必要になる値」をセッションだけに置いた結果、消えて別の処理にフォールバックし
  誤動作した実例がある（決済プランの選択情報）

## 第5条：ロジックは関数として切り出し、テストを書く

- バリデーション・判定ロジックなど、UIから独立できる処理は純粋関数として切り出す
- 切り出した関数にはユニットテスト（vitest）を書く。正常系・各必須項目の欠落・境界値を確認する
- UIの見た目やServer Action・DB・外部API呼び出し自体は無理にテストしない。
  「壊れると気づきにくい判定ロジック」に絞る

## 第6条：ブラウザ互換性、特にSafari/iOSを軽視しない

- フォームや画面を新規実装・修正する際は `CLAUDE.md` の「ブラウザ互換性」チェックリストを確認する
- 実機確認ができない場合は、原因をコード上の消去法で絞り込んだ上で、構造的な結論と
  未確認の部分を分けて正直に報告する（「〜である」と「〜の可能性が高い」を混同しない）

## 第7条：一時的な対応は役目を終えたら片付ける

- 調査用・移行用に作った一時スクリプトや管理用APIエンドポイントは、目的を達成したら削除する
- 一時的なコードにはコメントで「一時的である」ことと削除してよい条件を明記する

## 第8条：環境変数・秘密情報の扱い

- 本番とテストで環境変数（Stripeキー・DB接続・外部APIキー等）が混同されていないか、
  特に新しい連携を追加するときは確認する
- 秘密情報をチャットやログに生で貼らない。やり取りが必要な場合は共有方法自体を提案する

## ガバナンス

この文書より `CLAUDE.md`（技術的な規約・既知の罠）の方が更新頻度が高くなる想定です。
ここに書かれた原則と矛盾する実装判断をする場合は、その理由を記録してから進めてください。
